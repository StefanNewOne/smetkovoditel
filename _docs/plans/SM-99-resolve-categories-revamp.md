# SM-99 — Решавање читливост + менливи категории + продавачи по категорија

**Тип:** Modification (money-touching + schema) · **Гранка:** `feature/SM-99-resolve-categories`
**Кодови (Master Plan):** §4.2 (класификација/категоризација), §9.4 (Решавање), W9 (извештаи), B15/B16 (ADS/ACTORS pass-through)

## 1. Проблем (втемелен во реални податоци)

Делот **Решавање** содржи **373 неспарени излезни линии** + **12 влезни уплати**. Наодите од базата:

- **Влезни уплати:** `counterpartyName` е **секогаш `null`** (кастомниот НЛБ фонт ги гарбли кирилските имиња → парсерот ги отфрла). Останува само `counterpartyAccount` (ASCII, сигурно) + понекогаш повик. Се спаруваат само по (а) повик=фактура или (б) сметка→клиент (ClientBankAccount). 10 немаат ни повик ни поврзана сметка; 2 немаат ни сметка (шум).
- **Излезни трошоци — два вида:**
  - **CARD_TX** (картични): описот **го содржи продавачот** — „BP LISICE", „KOBRA-T", „BUJOGRADBA", „OPSTINA KISELA VODA". Читливо; `bankRef` носи код на картица.
  - **OTHER** (трансфери): описот е **празен**, има само сметка на примачот → **нечитливо од самата линија** („не знам кој трошок што е").
- **Правила за продавачи** = машина за авто-категоризација што учи (`pattern` во опис → категорија+продавач). Работи (K.VODA: 19 погодоци), но е прикажана како збунувачка рамна листа; неколку правила се гарблиран мртов товар (0 погодоци).
- **Категориите** се фиксен код-enum (13). Сопственикот сака да додава/преименува свои.

## 2. Одлуки за дизајн

**2.1 Категории: enum → табела `Category` (ХИБРИД — безбедност).**
`ExpenseCategory` не е само етикета: **ADS, ACTORS, SALARY, HONORAR, BANK_FEES** носат бизнис-логика (билирање B15/B16, плати W5, извештаи W9) низ 13 фајла. Ако се преименуваат/бришат, билирањето пука. Затоа:

- Нов модел `Category { key @id, label, system Boolean, kind, sortOrder, active }`.
- Seed на 13-те постоечки; **системските** (ADS, ACTORS, SALARY, HONORAR, BANK_FEES) добиваат `system=true` → клучот е непроменлив, не се бришат, само етикетата (label) се менува.
- **Сопствени** категории: сопственикот додава/преименува/деактивира слободно (`system=false`).
- `Expense.category` (enum) → `Expense.categoryKey` (String, реферира `Category.key`). Вредностите 1:1 остануваат („ADS"→„ADS"), па миграцијата е бездатна-загуба. Исто `VendorRule.category`.
- W9/извештаи групираат по `categoryKey`, етикетата преку join со `Category`.

**2.2 Читливоста доаѓа од контекст + изворен документ.** Сега кога сите 152 изводи се сервирливи, секој ред добива **„Види извод"** → го отвора PDF-от и ја гледаш линијата во контекст. Тоа е директното решение за „не знам кој трошок што е".

## 3. Опсег по делови

### Дел 1 — Читливо Решавање

- `lib/resolve.ts`: обогати ги `PaymentItem`/`ExpenseLineItem` со `statementNumber, date, description (цел), counterpartyAccount, bankRef, statementPdfUrl` (преку `attachment(import.fileRef)`).
- `resolve-view.tsx`: секој ред покажува извод № + датум, цел опис (продавач), сметка, + копче **„Види извод"**. За уплати: inline **„Поврзи сметка со клиент X → раздолжи"**.
- Нова акција `linkAccountAndSettleAction(lineId, clientId)` → создава `ClientBankAccount(counterpartyAccount→client)` + `runFifoOnUnmatched` (го генерализира АКТИВА-фиксот во UI, audit `match.fifo`).

### Дел 2 — Групирање + групно

- `lib/resolve.ts`: групирај ги излезните по продавач (CARD_TX) / сметка (OTHER).
- `resolve-view.tsx`: собирливи групи; **„категоризирај ги сите N како X"** + опција „научи правило".
- Нова акција `bulkCategorizeAction(lineIds[], categoryKey, rememberVendor)`.
- Мемо **сметка→продавач** за трансфери: при увоз, OTHER линиите се совпаѓаат со правило по `counterpartyAccount` (додади `VendorRule.matchAccount` или дозволи pattern да е сметка). Тогаш идните трансфери до иста сметка авто-категоризираат.

### Дел 3 — Подесувања: „Категории и продавачи"

- `lib/settings.ts`: врати категории (со број трошоци/погодоци) + правила **групирани по категорија**.
- `settings-view.tsx`: панел **Категории** — листа, додади (сопствена), преименувај етикета, деактивирај (не-системски); избери категорија → нејзините продавачи (додади/измени/избриши правило, види погодоци, избриши мртви).
- Акции: `createCategory, renameCategory, deactivateCategory, upsertVendorRule, deleteVendorRule` (сите `requireWriter`, audit).

## 4. Шема + миграција (рачно напишана, реверзибилна)

1. `CREATE TABLE "Category"` + seed на 13 (системски флагирани).
2. `ALTER TABLE "Expense" ALTER COLUMN "category" TYPE text USING category::text` → преименувај во `categoryKey` (или задржи име, смени тип). Исто `VendorRule`.
3. `DROP TYPE "ExpenseCategory"` откако колоните се текст.
4. FK `Expense.categoryKey → Category.key` (`onDelete: Restrict`), исто VendorRule.
5. Ажурирај ги 13-те фајла: `w1, w2, w5, w6, w9, meta, expenses(CATEGORY_LABEL→Category), settings, schemas(Zod), seed, resolve/actions, settings/actions` + тестот `resolve-categorize`.

## 5. Критериуми за прифаќање

- **AC1:** секој ред во Решавање покажува извод № + датум + сметка + „Види извод" што го отвора точниот PDF.
- **AC2:** уплата со непозната сметка → „Поврзи со клиент X" ја создава врската + ја раздолжува најстарата фактура (FIFO), редот исчезнува.
- **AC3:** „категоризирај ги сите N од BP LISICE како ГОРИВО" создава N трошоци + (опц.) едно правило; повторен увоз не дуплира (идемпотентно).
- **AC4:** Подесувања → избери ГОРИВО → ги гледаш Makpetrol/Lukoil/BP; можеш да додадеш/избришеш продавач.
- **AC5:** можеш да додадеш **сопствена** категорија и да ја избереш во Решавање; **не** можеш да ја избришеш/преименуваш клучот на системска (ADS/ACTORS/SALARY/HONORAR/BANK_FEES).
- **AC6:** W9 извештаите работат непроменето (групирање по key, етикета преку Category); сите постоечки тестови зелени + нови тестови за категории/групно.

## 6. Ризици / rollback

- **Најголем ризик:** прекин на ADS/ACTORS билирањето. Ублажено со `system` флаг (клуч непроменлив/незбришлив) + тестови T12–T14 остануваат.
- Миграцијата е наназад-компатибилна (enum→string 1:1). Rollback: врати enum од текст (вредностите се валидни).
- Извештаите: `kind` на категоријата (OPERATING/BILLABLE/PAYROLL/BANK) овозможува P&L групирање да остане стабилно и за сопствени категории.
